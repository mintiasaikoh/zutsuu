# グローバル iOS アプリ設計

作成日: 2026-08-30

## 1. 目的

既存の zutsuu（GitHub Actions で毎時実行し、単一ユーザーに LINE 通知する個人用スクリプト）を、
世界中で使える iOS アプリとして作り直す。

競合は頭痛ーる。差別化の軸は 3 つ。

1. **軽さ** — 起動して即座にリスクが読める。広告で重くしない。
2. **パーソナライズ** — 使うほど自分の閾値に合っていく。競合は記録して終わり。
3. **プライバシー** — 位置情報も健康データも端末外に出ない。

収益は広告のみ。課金・サブスクリプションは行わない。

### 既知のトレードオフ

広告除去の手段を提供しないため、「広告が多い」「消せない」という低評価レビューは確実に発生する。
これはランキングに影響する既知のコストとして受け入れる。§7 の Tier 0（聖域）が唯一の防波堤。

## 2. 決定事項

| 項目 | 決定 |
|------|------|
| プラットフォーム | iOS ネイティブ（Swift / SwiftUI）+ watchOS |
| バックエンド | 持たない。端末完結。必要になった時点で追加できる構造にする |
| 収益 | 広告のみ。IAP・サブスクなし |
| 広告 SDK | 初回は AdMob 単体。メディエーションは DAU が立ってから |
| 言語 | 日本語・英語・ドイツ語・韓国語・中国語の 5 言語 |
| 主データ源 | Apple WeatherKit（§11 の調査で確定） |
| 気圧平年値 | 静的テーブルをアプリに同梱（NOAA 再解析ベース） |
| 補助データ源 | v1.0 では持たない（気象庁 bosai は §11.4 の理由で見送り） |
| リスク段階 | 4 段階（既存コードに合わせる。`SPEC.md` の 5 段階記述は古い） |

│  │ RiskEngine  │        │  AdProvider      │    │
│  │ 相関エンジン │  ╳ ← 型レベルで到達不能 → │  (AdMob)         │    │
│  │ HealthKit   │        │                  │    │

サーバーを持たないため、ユーザーデータが外部に出る経路が構造的に存在しない。
これは §8 のコンプライアンス要件を「運用で守る」ではなく「設計で保証する」ことを可能にする。

### モジュール分離の強制

`RiskEngine` / 相関エンジン / HealthKit ラッパーを含むモジュールは、広告モジュールに依存しない。
Swift Package として分け、広告側から健康データ型へ到達できないようにする。
これは §8 の HealthKit 規約を満たすための必須要件であり、単なる整理ではない。

## 4. 通知設計 — 事前予約モデル

本アプリの中核。頭痛ーるに対する構造的な優位はここにある。

### 従来型との違い

競合はサーバーが全ユーザーの地点を監視し、条件成立時に push を送る。
サーバー費用が発生し、位置情報を預かる責任も生じる。

本アプリは逆に、**予報を先に取得して端末上でローカル通知を予約する**。

```
アプリ起動 or BGAppRefreshTask
    ↓
今後 72 時間の気象データを一括取得
    ↓
端末上で毎時のリスクスコアを計算
    ↓
リスクが 3 以上に上がる時刻を検出
    ↓
その 1〜2 時間前に UNNotificationRequest を予約
    ↓
既存の予約はキャンセルして貼り直す
```

### なぜ確実なのか

`BGAppRefreshTask` は OS 都合で実行されないことがある。これが iOS のバックグラウンド処理の最大の弱点。

しかし本方式では、**最後にアプリを開いた時点で最大 72 時間分の通知が既に予約済み**である。
バックグラウンド更新が一度も走らなくても通知は途切れない。
機内モード・圏外でも予約済みの通知は発火する。

気圧は 72 時間先まで予報精度が十分高いため、この前倒しが成立する。

### 制約

- iOS の保留中ローカル通知は 64 件が上限。実際の予約は 1 日あたり 2〜3 件なので余裕がある
- 予報更新で条件が消えた場合、予約済み通知は必ずキャンセルする（外れ通知は信頼を最も損なう）
- 静穏時間（既定 22:00〜08:30、端末ローカル時刻）内の通知は予約しない。ユーザーが変更可能

## 5. リスクエンジンのグローバル対応

既存の `computeCompositeRisk()` を Swift へ移植する。ただしグローバル化で 4 点の修正が必要。

### 5.1 絶対気圧の閾値 — 固定値をやめる

既存コードは `pressure <= 1005` を固定閾値としている（[src/index.ts:161](src/index.ts:161)）。
これは日本の温帯気候を前提とした値で、そのまま世界に出すと破綻する。

- 熱帯（赤道付近）は年間を通して平均気圧が低く、**常時アラート状態**になる
- 冬季の内陸高緯度（シベリア、モンゴル）は 1030hPa 超が常態で、**絶対に発火しない**

**解決：地点ごとのパーセンタイル評価に置き換える。**

**気圧平年値の静的テーブルをアプリに同梱する。**

当初は過去 90 日分を API から取得する案だったが、§11 の調査により取得元が確保できなくなったため方式を変更した。
NOAA NCEP/NCAR 再解析の月別平均海面気圧はパブリックドメインで、
粗い格子（2.5 度）であれば月別の平均と標準偏差を持っても 1MB 未満に収まる。

これをバンドルすることで、ネットワーク通信なし・遅延ゼロで、世界中のどの地点でも即座に基準値が得られる。
オフラインでも成立し、季節変動も月別テーブルで吸収できる。

| 現在値の位置 | スコア |
|---|---|
| 下位 10% 未満 | +3 |
| 下位 10〜25% | +2 |
| 下位 25〜40% | +1 |

「その土地としては低い」を評価するので、どの気候帯でも同じ意味になる。

副次的に**高地問題も同時に解決する**。メキシコシティやラパスのような高標高地では
海面更正気圧と実際の体感気圧が大きく乖離するが、分布の相対位置で見る限り影響を受けない。

なお気圧の**変化量**スコア（1h/3h/6h）は既存の固定閾値のままでよい。
変化量は標高・気候帯によらず同じ意味を持つ。

### 5.2 タイムゾーン

既存は `Asia/Tokyo` 決め打ち（[src/index.ts:126](src/index.ts:126)）で、時刻判定も端末ローカル時刻に依存している。
端末のタイムゾーンを使い、API へも明示的に渡す。静穏時間・朝の予報時刻もすべて端末ローカル基準。

### 5.3 単位系

初期値をロケールから推定し、設定で変更可能にする。

| 地域 | 気温 | 気圧 |
|---|---|---|
| 米国 | °F | inHg |
| その他 | °C | hPa |

### 5.4 気象庁連携は v1.0 では行わない

既存の気象庁ナウキャスト（`hrpns` タイル）と降水確率は日本国内限定で、
エンドポイントも東京（`130000`）にハードコードされている（[src/index.ts:195](src/index.ts:195)）。

利用規約上は商用利用可能だが、§11.4 の理由により v1.0 では組み込まない。
WeatherKit の分単位降水予報が日本で利用可能であれば、そちらで代替する。

## 6. パーソナライズ

### 6.1 記録は「日記」ではない

日記アプリにすると続かない。続かなければデータが溜まらず、この機能全体が無価値になる。

**メイン画面で今日の体調を 1 タップ、2 秒で完了**まで削る。自由記述は任意のおまけ。
記録 UI は Tier 0（広告なし）に置く。

### 6.2 フィードバックループ

```
1 タップ記録 → 個人の相関が出る → その人専用のリスク閾値に補正
   ↑                                              ↓
   └────── 記録する動機になる ←── 通知が当たるようになる
```

競合の痛みノートは記録して終わりで、予報側にフィードバックされない。ここが構造的な差。
使うほど自分に合っていくため、継続率が上がり、結果として広告在庫も増える。

### 6.3 統計的な誠実さ

これは守るべき線。破ると製品の信頼が失われ、審査でも問題になる。

- **最小サンプル数に達するまで相関レポートを出さない。** n=14 では相関とは呼べない。
  実用的には 30〜60 日分が必要
- 到達までは「あと 18 日分で解析できます」と進捗表示する。これ自体が継続の動機になる
- 出力は**予測ではなく記述**に留める。「あなたの記録ではこう出ています」であって「予測します」ではない
- 交絡因子（睡眠・ストレス・月経周期）が支配的なケースが普通にある。§7 の HealthKit 連携はこの問題への直接的な回答

### 6.4 記録ゼロでも成立させる

初日から価値が必要。**記録が 1 件もなくても汎用リスクスコアだけで完結して使える**状態を必ず保つ。
既存の `src/index.ts` のロジックがそのまま初日の価値を担う。
パーソナライズは「使い込むと効いてくる上積み」。

## 7. Apple Watch / HealthKit

### 7.1 なぜ効くのか

§6.3 で挙げた交絡因子の問題を、推測ではなく**実測**で解決できる。

特に **HRV（心拍変動）** が重要。気象病の機序は「気圧変化 → 交感神経の過剰興奮 → 自律神経の乱れ」であり、
HRV はまさにその自律神経のバランス指標。機序の中心に計測値が対応している。

| HealthKit データ | 役割 |
|---|---|
| HRV (SDNN) | 自律神経の状態。気圧変化への反応 |
| 安静時心拍数 | ベースラインからの逸脱 |
| 睡眠時間・睡眠段階 | 片頭痛の主要トリガー。交絡因子の実測 |
| 手首皮膚温 | Series 8 以降。体調変動の指標 |
| 月経周期 | 女性ユーザーでは気圧より支配的なことがある |

相関エンジンの入力が「気圧のみ」から「気圧 × 睡眠 × HRV × 周期」になることで、
「気圧が下がる日でも、睡眠が取れていれば出ない」といった個人ルールまで導出できる。

記録を HealthKit の頭痛カテゴリへ書き戻し、ヘルスケアアプリ側からも見えるようにする。

### 7.2 収益との関係

watchOS に広告 SDK は存在しない。
さらに文字盤コンプリケーションでリスクが見えると、ユーザーは iPhone アプリを開かなくなる。
1 セッションあたりの広告面数だけを見れば明確なマイナス。

しかし広告収益は `DAU × 面数` で決まる。
**文字盤に常駐して毎日目に入り、アンインストールされない**効果のほうが大きい。
継続率が 2 倍になれば面数が半分でも上回る。コンプリケーションは収益的にもプラスと判断する。

その上で線引きする。

- コンプリケーションはリスクレベルのみ表示（Tier 0 相当の情報）
- Watch 通知の詳細を見るタップ先は iPhone アプリ
- 相関レポート・詳細予報・複数地点は iPhone のみ = 広告面を温存
- **Watch 連携そのものをリワード広告の後ろに置かない。** 体調系の中核機能を広告と交換させない

### 7.3 遵守すべき制約

**HealthKit のデータを広告に利用することは App Store の規約で明確に禁止されている。**
広告一本で収益を立てる以上、ここは事故ればリジェクト事由になる。

§3 のモジュール分離により、広告 SDK が動くモジュールから健康データ型へ型レベルで到達できないようにする。
サーバーを持たないため、そもそも外部へ送出する経路が存在しない。

## 8. 広告設計 — 4 層モデル

### 8.1 前提の確認

気象病アプリは 1 セッション 10〜30 秒。「今日どう？」を見て閉じる。
**画面遷移の回数で広告を稼ぐのは物理的に成立しない。**
ここを見誤ると遷移を水増しする設計になり、競合と同じ体験になる。

方針は「面を増やす」ではなく、**自発的に潜りたくなる深さを作り、そこへ広告を集中させる**。

### 8.2 層構成

**Tier 0 — 広告を置かない聖域**

起動直後のメイン画面（今日のリスク）、通知タップで開いた画面、1 タップ記録 UI。
広告ゼロ・通信ゼロ・キャッシュから即描画。

体調が悪いときに開く画面だから。競合との差はこの 1 画面で付き、低評価レビューへの防波堤にもなる。

**Tier 1 — インフィード・ネイティブ広告**

時間別リスト、週間予報リストの中に数件おきに 1 枠。
スクロールで可視域に入って初めてロードする。
バナーより単価が高く、レイアウトを自分で組めるので表示がガタつかない。

**Tier 2 — インタースティシャル**

画面遷移時。頻度制御がすべて。

- 起動後の最初の遷移では出さない
- 遷移 4 回ごと
- 前回表示から 3 分以上
- 1 日 6 回まで
- 通知経由の起動は遷移カウントに含めない

AdMob は予期しない全画面広告をポリシー違反としているため、この制御は収益とコンプライアンスの両面で必須。

**Tier 3 — リワード動画**

主力。ユーザーが自分で押すため不満が出にくく、単価も全フォーマット中で最も高い。

| 解放するもの | 期限 |
|---|---|
| 個人相関レポート | 7 日間 |
| 地点の追加（2 件目以降） | 30 日間 |
| 7 日先の詳細予報 | 24 時間 |
| 過去ログのグラフ表示 | 7 日間 |

期限付きにするのは再収益化のため。ただし短すぎると嫌がらせになるので上記が上限。

**App Open 広告**

コールドスタートでは出さない（起動体感を殺す最大要因）。
バックグラウンド復帰時のみ、かつ前回表示から 4 時間以上経過している場合に限る。通知経由の起動は除外。

### 8.3 軽さを守る実装上の要件

- Google Mobile Ads SDK の初期化は**メイン画面の描画完了後に非同期実行**。起動のクリティカルパスに乗せない
- 広告表示は `AdProvider` プロトコル 1 枚に閉じ込め、後からメディエーションへ差し替えても画面側を触らずに済むようにする
- 初回リリースは AdMob 単体。DAU がゼロの新規アプリでは他ネットワークがフィルを返さないため、
  メディエーションは実装と同意管理の負担だけが先行する。トラフィックが立ってから追加する

## 11. データ源の調査結果（2026-08-30 実施）

当初案の Met.no / Open-Meteo は**いずれも本アプリでは使えない**ことが判明した。
両者ともサーバーの設置を要求するため、§3 のサーバーレス設計が成立しなくなる。
代替として Apple WeatherKit を採用する。

### 11.1 Open-Meteo — 使用不可

利用規約で、広告を表示するアプリは明確に商用利用と定義されている。

> "You may only use the free API services for non-commercial purposes."

商用にあたる例として "Operating websites or apps that have subscriptions or **display advertisements**" が挙げられている。
本アプリは広告のみで収益を立てるため、無料枠は使えない。

有料プランは `customer-api.open-meteo.com` への API キーが発行される方式。
キーをアプリのバイナリへ埋め込むと抽出されるため、プロキシサーバーが必須になる。

### 11.2 Met.no — 使用不可

API キーは不要で商用利用の明示的な禁止もないが、規約が**モバイルアプリからの直接アクセスを否定している**。

> "Browsers and mobile apps should not contact the API directly, but instead use a local proxy (backend for frontend) server."

さらにレート制限が「アプリ全体で 20 req/s（クライアント単位ではない）」と規定されており、
ユーザー数が増えた時点で規約違反が避けられない構造になっている。

> "Anything over 20 requests/second per application (total, not per client) requires special agreement."

キーが不要な点だけを見て採用すると、スケールした瞬間に破綻する。

### 11.3 Apple WeatherKit — 採用

iOS 専用アプリであることが、ここで決定的な利点になる。

| 項目 | 内容 |
|---|---|
| 呼び出し方 | Swift の第一者フレームワーク。端末から直接呼ぶのが正規の使い方 |
| API キー | 不要（entitlement ベース）。バイナリ埋め込み問題が存在しない |
| 気圧 | `pressure` = 海面気圧（ミリバール = hPa）。`pressureTrend` も提供 |
| その他 | 気温・湿度・降水確率・10 日先までの毎時予報。リスクエンジンの入力を全て満たす |
| カバー範囲 | 全球 |
| 商用利用 | 可 |

### 11.4 気象庁 — v1.0 では見送り

利用規約自体は問題ない。政府標準利用規約（公共データ利用規約 第1.0版）に準拠しており、
**商用利用は可能**。ただし「出典：気象庁ホームページ（URL）」の表示と、加工した場合はその旨の明記が必要。

見送る理由は規約ではなく実装リスク。
既存コードが叩いている `www.jma.go.jp/bosai/...` は公式に API として提供されているものではなく、
気象庁サイト自身が使う内部エンドポイントである。予告なく変更・停止される可能性があり、
アプリから大量にアクセスする使い方は想定されていない。

WeatherKit の分単位降水予報（一部地域）が日本で利用可能であれば、そちらで代替する。

### 11.6 WeatherKit のスケールの罠（Plan 2 の必須要件）

コードレビューで判明した、静かに壊れる種類の不具合。

WeatherKit の `humidity` と `precipitationChance` は **0...1 の比率**で提供される。
一方 RiskEngine のスコアリング閾値は既存 TS 実装を引き継いで **0〜100** を前提としている
（湿度 75 以上、降水確率 60 以上など）。

アダプタ層で 100 倍を忘れると、湿度スコアと降水スコアが**恒久的に 0 のまま**になる。
例外も警告も出ず、ただアラートが発火しなくなるだけなので、最も発見が遅れる壊れ方をする。

範囲バリデーションでは検出できない点に注意。誤って `0.85` が渡された場合でも
`0...100` の範囲内に収まってしまうため、クランプも `precondition` も無力である。

**したがって Plan 2 のアダプタには、変換が行われていることを検証するテストを必ず含める。**
具体的には、WeatherKit 相当の入力（`humidity: 0.85`）を与えたとき
`WeatherPoint.humidity == 85` になることを確認するテスト。
