# グローバル iOS アプリ設計

作成日: 2026-08-30

## 1. 目的

既存の zutsuu（GitHub Actions で毎時実行し、単一ユーザーに LINE 通知する個人用スクリプト）を、
世界中で使える iOS アプリとして作り直す。

競合は頭痛ーる。差別化の軸は 3 つ。

1. **軽さ** — 起動して即座にリスクが読める。広告で重くしない。
2. **パーソナライズ** — 使うほど自分の閾値に合っていく。競合は記録して終わり。
3. **プライバシー** — 位置情報も健康データも端末外に出ない。

収益は広告のみ。課金・サブスクリプションは行わない。

### 既知のトレードオフ

広告除去の手段を提供しないため、「広告が多い」「消せない」という低評価レビューは確実に発生する。
これはランキングに影響する既知のコストとして受け入れる。§7 の Tier 0（聖域）が唯一の防波堤。

## 2. 決定事項

| 項目 | 決定 |
|------|------|
| プラットフォーム | iOS ネイティブ（Swift / SwiftUI）+ watchOS |
| バックエンド | 持たない。端末完結。必要になった時点で追加できる構造にする |
| 収益 | 広告のみ。IAP・サブスクなし |
| 広告 SDK | 初回は AdMob 単体。メディエーションは DAU が立ってから |
| 言語 | 日本語・英語・ドイツ語・韓国語・中国語の 5 言語 |
| 主データ源 | Apple WeatherKit（§11 の調査で確定） |
| 気圧平年値 | 静的テーブルをアプリに同梱（NOAA 再解析ベース） |
| 補助データ源 | v1.0 では持たない（気象庁 bosai は §11.4 の理由で見送り） |
| リスク段階 | 4 段階（`src/index.ts` に合わせる。`SPEC.md` / `CLAUDE.md` も修正済み） |

サーバーを持たないため、ユーザーデータが外部に出る経路が構造的に存在しない。
これは §8 のコンプライアンス要件を「運用で守る」ではなく「設計で保証する」ことを可能にする。

### モジュール分離の強制

`RiskEngine` / 相関エンジン / HealthKit ラッパーを含むモジュールは、広告モジュールに依存しない。
Swift Package として分け、広告側から健康データ型へ到達できないようにする。
これは §8 の HealthKit 規約を満たすための必須要件であり、単なる整理ではない。

## 4. 通知設計 — 事前予約モデル

> **実装の正確な仕様は [`docs/riskengine-api.md`](../riskengine-api.md) を参照。**
> 本節は設計判断とその理由を記す。API のシグネチャや閾値の参照元にはしないこと。

本アプリの中核。頭痛ーるに対する構造的な優位はここにある。

### 従来型との違い

競合はサーバーが全ユーザーの地点を監視し、条件成立時に push を送る。
サーバー費用が発生し、位置情報を預かる責任も生じる。

本アプリは逆に、**予報を先に取得して端末上でローカル通知を予約する**。

```
アプリ起動 or BGAppRefreshTask
    ↓
今後 72 時間の気象データを一括取得
    ↓
端末上で毎時のリスクスコアを計算
    ↓
リスクが 3 以上に上がる時刻を検出
    ↓
その 1〜2 時間前に UNNotificationRequest を予約
    ↓
既存の予約はキャンセルして貼り直す
```

### なぜ確実なのか

`BGAppRefreshTask` は OS 都合で実行されないことがある。これが iOS のバックグラウンド処理の最大の弱点。

しかし本方式では、**最後にアプリを開いた時点で最大 72 時間分の通知が既に予約済み**である。
バックグラウンド更新が一度も走らなくても通知は途切れない。
機内モード・圏外でも予約済みの通知は発火する。

気圧は 72 時間先まで予報精度が十分高いため、この前倒しが成立する。

### 予約ルール（実装で確定）

初版の「リスクが上がる 90 分前に予約、静穏時間なら予約しない」という素朴な規則は、
実装時の検証で**通知の大半が届かない**ことが判明したため、以下に置き換えた。

リスクが閾値（注意レベル）以上へ上がる各時点について:

1. 対象時刻が既に過去なら破棄（等号も破棄）
2. 発火時刻 = 対象時刻 − 90 分（絶対時刻演算）
3. 発火時刻が現在以前なら、現在＋猶予（60 秒）へ繰り上げる
4. **5a** 繰り上げの結果、発火時刻が対象時刻以降になったなら破棄
5. **発火時刻が静穏時間内なら、静穏時間の終了時刻へ繰り下げる**（破棄しない）
6. **5b** 繰り下げの結果、発火時刻が対象時刻以降になったなら**起床時通知に変換**（破棄しない）

**5a と 5b の非対称が仕様の中心。** 繰り上げ由来の追い越しは破棄、繰り下げ由来の追い越しは変換。
前者は差し迫ったイベント、後者は就寝中に到来したイベントであり、扱いが異なる。

破棄経路は 3 つだけ（規則 1、規則 5a、規則 5 の移動先が求まらない場合）。

**繰り下げ（規則 4）を繰り上げ（規則 3）より後に置くこと。** 逆順だと、静穏時間が
リードタイムより短い設定で破綻する。反例: 昼寝 13:00〜13:30、対象 14:00、現在 13:10。
素の発火 12:30 は静穏時間外なので繰り下げが起きず、規則 3 で 13:11 へ繰り上がって
**昼寝の最中に鳴る**。繰り下げを最後に置けば 13:30 となり、
「静穏時間内には鳴らさない」が無条件に成立する。

**規則 4 がなぜ必要か。** 素朴版では発火時刻が [22:00, 08:30) に入る条件が
「対象時刻 ∈ [23:30, 10:00)」となり、**朝 9 時台のリスク上昇まで無警告**になっていた。
静穏時間の意図は「夜に鳴らすな」であって「朝のイベントを警告するな」ではない。
規則 4 により 09:00 の上昇は 08:30 に通知される。

**就寝中に到来するイベントも破棄しない。** 一度は「対象時刻が静穏時間内なら破棄」という
規則を置いたが、実装時の検証で削除した。冗長か有害のどちらかにしかならないため。

- 対象 03:00 → 発火 01:30 が静穏内 → 規則 5 が 08:30 へ繰り下げ → 規則 5b が**起床時通知に変換**
- 対象 23:00 → 発火 21:30 は静穏**外** → この規則だけが破棄していた

後者は残すべきケースである。頭痛薬の予防内服は前もって飲むほど効くため、
「23 時に気圧が急降下する、寝る前に飲んでおけ」は本アプリが送れる最も価値の高い通知に属する。
発火時刻が起床中であれば、対象時刻が就寝中でも行動できる瞬間は存在する。

**規則 3 がなぜ必要か。** 素朴版には「現在」の概念がなく、予報開始 12:00 の曲線に対して
発火時刻 11:30 を返していた。`UNTimeIntervalNotificationTrigger` は過去時刻で例外を投げる。
しかも失われるのは**最も緊急な直近の上昇**である。破棄ではなく即時通知にするのは、
差し迫った上昇こそ知る価値が最も高いため。

### 就寝中のイベントは起床時に通知する

規則 4 と 5 の合成には穴があった。onset が概ね 23:30〜08:30 のイベントは
**1 件も通知されない**。規則 4 が発火時刻を静穏明けへ繰り下げ、
規則 5 がその時刻は対象を追い越していると見て「リードが取れない」と破棄するため。
30 分刻みで全掃引すると 48 枠中 19 枠、一日の約 9 時間分が該当した。

**規則 5 を「破棄」から「起床時通知への変換」に変える。**
ただし追い越しの原因が規則 4（静穏繰り下げ）の場合に限る。
規則 3（現在時刻への繰り上げ）が原因の場合は従来どおり破棄する
——そちらは差し迫ったイベントであって、寝過ごしたイベントではない。

| onset | 発火 | 種別 |
|---|---|---|
| 23:00 | 21:30（静穏外。繰り下げが起きない） | 事前警告 |
| 09:00 | 08:30（繰り下げ後も対象に間に合う） | 事前警告 |
| 03:00 | 08:30（繰り下げが対象を追い越す） | **起床時通知** |
| 00:30 | 08:30（同上） | **起床時通知** |

**なぜ破棄が誤りだったか。** リードタイムを唯一の価値と見なしていたのが誤り。
本アプリの目的は「薬を飲むタイミングを知らせる」ことであり、
気圧が既に下がった後でも、起きた時点で飲むという行動は成立する。
リードがゼロでも価値はゼロではない。

逆に、就寝前に翌朝 3 時のイベントを予告しても、起きた頃には忘れている。
事前警告が機能するのは、発火時刻に本人が起きている場合に限られる。

**通知の種別を `ScheduledAlert` が持つ。** アプリ層は文面を出し分ける必要があり、
さらに **`fireDate` と `targetDate` の前後関係が種別によって反転する**。
事前警告は `fireDate < targetDate`、起床時通知は **`fireDate >= targetDate`**（境界では同時刻）。
下流でこの順序を仮定しているコードは起床時通知で誤る。

**一晩に複数のイベントがあっても起床時通知は 1 件にまとめる。**
起きた瞬間に通知が 3 件並ぶのは、解決しようとしている問題より悪い体験になる。
判定内容は最もスコアの高いもの、対象時刻は最も早いもの（＝乱れが始まった時刻）を使う。
したがって両者は別の時点を指しうる。

集約キーは**発火時刻の厳密一致**であり、「同じ夜」という単位は実装に存在しない。
**事前警告は集約しない** — 09:00 と 10:00 に別々のエピソードがあると、
どちらも繰り下げで発火 08:30 になり、同時刻に 2 通が返る。

### 文面の制約 — 睡眠中の影響を主張しない

「睡眠中に気圧の影響を受けたか」を調べたが、**直接測定した研究は見つからなかった**。

想定機序（内耳の気圧センサー → 自律神経の反応）は覚醒を必要としないため、
理屈の上では睡眠中も成立するはずである。しかし朝の頭痛発症について主流の説明は
概日リズムと睡眠に関するものであり、気圧ではない。
加えて内耳センサー説そのものが日本の臨床モデル寄りで、
気圧と片頭痛の関連を扱った系統的レビューの結果も一貫していない。

したがって `.wakeUp` という種別名は**通知が発火する時刻を指すのであって、
生理学的な主張ではない**。文面は事実に留める。

- 良い: 「睡眠中に気圧が 8hPa 下がりました」
- 不可: 「睡眠中に気圧の影響を受けました」

§6.3 の「予測ではなく記述」という制約が、母集団レベルの証拠がこれだけ弱い以上、
想定より重要であることの裏付けでもある。個人の記録から出す相関のほうが
一般則より情報量が多い、という §6 の設計判断を補強する。

### 1 イベント 1 通知

閾値以上が連続する区間を 1 つの荒天イベントとして扱い、通知は 1 件にまとめる。
対象時刻は最初に閾値を超えた時刻、レベルはその区間の最大値を使う。

素朴版では `安心→やや注意→注意→危険` という緩やかな上昇で 2 件、
閾値をまたいで振動する曲線ではさらに増え、1 つの荒天で通知が連投される状態だった。

### その他の制約

- iOS の保留中ローカル通知は 64 件が上限。実際の予約は 1 日あたり 2〜3 件なので余裕がある
- 予報更新で条件が消えた場合、予約済み通知は必ずキャンセルする（外れ通知は信頼を最も損なう）
- 静穏時間は既定 22:00〜08:30、端末ローカル時刻。ユーザーが変更可能
- リードタイムの計算は絶対時刻演算、静穏時間の判定は壁時計。
  夏時間の切替を跨いでも前者は実時間 90 分、後者は現地時刻で正しく判定される

## 5. リスクエンジンのグローバル対応

既存の `computeCompositeRisk()` を Swift へ移植する。ただしグローバル化で 4 点の修正が必要。

### 5.1 絶対気圧の閾値 — 固定値をやめる

既存コードは `pressure <= 1005` を固定閾値としている（[src/index.ts:161](src/index.ts:161)）。
これは日本の温帯気候を前提とした値で、そのまま世界に出すと破綻する。

- 熱帯（赤道付近）は年間を通して平均気圧が低く、**常時アラート状態**になる
- 冬季の内陸高緯度（シベリア、モンゴル）は 1030hPa 超が常態で、**絶対に発火しない**

**解決：地点ごとのパーセンタイル評価に置き換える。**

**気圧平年値の静的テーブルをアプリに同梱する。**

当初は過去 90 日分を API から取得する案だったが、§11 の調査により取得元が確保できなくなったため方式を変更した。
NOAA NCEP/NCAR 再解析の月別平均海面気圧はパブリックドメインで、
粗い格子（2.5 度）であれば月別の平均と標準偏差を持っても 1MB 未満に収まる。

これをバンドルすることで、ネットワーク通信なし・遅延ゼロで、世界中のどの地点でも即座に基準値が得られる。
オフラインでも成立し、季節変動も月別テーブルで吸収できる。

| 現在値の位置 | スコア |
|---|---|
| 下位 10% 未満 | +3 |
| 下位 10〜25% | +2 |
| 下位 25〜40% | +1 |

「その土地としては低い」を評価するので、どの気候帯でも同じ意味になる。

副次的に**高地問題も同時に解決する**。メキシコシティやラパスのような高標高地では
海面更正気圧と実際の体感気圧が大きく乖離するが、分布の相対位置で見る限り影響を受けない。

なお気圧の**変化量**スコア（1h/3h/6h）は既存の固定閾値のままでよい。
変化量は標高・気候帯によらず同じ意味を持つ。

### 5.2 タイムゾーン

既存は `Asia/Tokyo` 決め打ち（[src/index.ts:126](src/index.ts:126)）で、時刻判定も端末ローカル時刻に依存している。
端末のタイムゾーンを使い、API へも明示的に渡す。静穏時間・朝の予報時刻もすべて端末ローカル基準。

### 5.3 単位系

初期値をロケールから推定し、設定で変更可能にする。

| 地域 | 気温 | 気圧 |
|---|---|---|
| 米国 | °F | inHg |
| その他 | °C | hPa |

### 5.4 気象庁連携は v1.0 では行わない

既存の気象庁ナウキャスト（`hrpns` タイル）と降水確率は日本国内限定で、
エンドポイントも東京（`130000`）にハードコードされている（[src/index.ts:195](src/index.ts:195)）。

利用規約上は商用利用可能だが、§11.4 の理由により v1.0 では組み込まない。
WeatherKit の分単位降水予報が日本で利用可能であれば、そちらで代替する。

## 6. パーソナライズ

### 6.1 記録は「日記」ではない

日記アプリにすると続かない。続かなければデータが溜まらず、この機能全体が無価値になる。

**メイン画面で今日の体調を 1 タップ、2 秒で完了**まで削る。自由記述は任意のおまけ。
記録 UI は Tier 0（広告なし）に置く。

### 6.2 フィードバックループ

```
1 タップ記録 → 個人の相関が出る → その人専用のリスク閾値に補正
   ↑                                              ↓
   └────── 記録する動機になる ←── 通知が当たるようになる
```

競合の痛みノートは記録して終わりで、予報側にフィードバックされない。ここが構造的な差。
使うほど自分に合っていくため、継続率が上がり、結果として広告在庫も増える。

### 6.3 統計的な誠実さ

これは守るべき線。破ると製品の信頼が失われ、審査でも問題になる。

- **最小サンプル数に達するまで相関レポートを出さない。** n=14 では相関とは呼べない。
  実用的には 30〜60 日分が必要
- 到達までは「あと 18 日分で解析できます」と進捗表示する。これ自体が継続の動機になる
- 相関**レポート**の文面は**記述**に留める。「あなたの記録ではこう出ています」であって「予測します」ではない
- 予測は**条件付きで解禁**する（2026-09-09 改訂。当初は全面不使用だった）。条件: (1) 事前分布への縮小推定で、記録が少ないほど汎用スコアに一致すること（nの閾値で挙動が急変しない） (2) 適用先は通知閾値の補正のみで、画面のリスクレベル表示は汎用のまま (3) 重みの符号を制約し「悪天候ほど安全」という方向の学習をしないこと。詳細は §6.5
- 交絡因子（睡眠・ストレス・月経周期）が支配的なケースが普通にある。§7 の HealthKit 連携はこの問題への直接的な回答

### 6.4 記録ゼロでも成立させる

初日から価値が必要。**記録が 1 件もなくても汎用リスクスコアだけで完結して使える**状態を必ず保つ。
既存の `src/index.ts` のロジックがそのまま初日の価値を担う。
パーソナライズは「使い込むと効いてくる上積み」。

### 6.5 パーソナライズ回帰予測（2026-09-09 決定）

汎用リスクスコアに加えて、本人の体調記録から学習した回帰予測を通知判定に使う。

- **モデル**: オンデバイスのロジスティック回帰。目的変数は記録時点の体調（悪い=1）、
  説明変数はリスク要因の 5 点数（気圧変化・気圧ベースライン・湿度・降水・気温変動）
- **事前分布 = 文献で較正した汎用スコア**（2026-09-11 改訂。当初は全要因の重み 1 の汎用そのもの）。
  切片 −4 を中心とした MAP 推定。記録ゼロなら較正済み事前分布と一致し、溜まるほど個人へ連続的に寄る。
  §6.4「記録ゼロでも成立」と §6.3 の誠実さを、n の閾値ではなく縮小推定で同時に満たす
- **較正の中身**: 集団データの効果量（`docs/research/2026-09-10-population-datasets.md`、
  仕様書参考文献 [1][4]）から、要因の重み比を 気圧変化 1.0 / 絶対気圧 0.9 / 湿度 1.3 / 降水 0.6 /
  気温変動 0.6 とする。比は文献からの**専門家較正であり導出ではない**。
  重みは「満点 18pt の logit が汎用と同じ」になるよう正規化するので、0pt と 18pt では汎用と確率が
  一致し、中間の配分だけが傾く。通知判定と表示レベルの差は全組み合わせで最大 1 段
  （テストで固定）。表示用の 18pt 表は触らない — 表示の透明性は保ち、個人化はこの上に乗る
- **失ったもの**: 「記録ゼロなら通知判定と表示レベルが完全一致」は成り立たなくなった。
  代わりに「0pt・18pt で一致、差は 1 段以内」を性質として固定する
- **適用先は通知閾値の補正のみ**（画面表示は汎用のまま）。効果が「通知が出る/出ない」に
  限定されるため説明可能で、外したときの被害も通知 1 件に留まる
- **副産物**: 学習済みの重みがそのまま「あなたは湿度に反応しやすい」という
  説明可能な相関レポートになる。ブラックボックスな予測モデルは導入しない
- **安全弁**: 重みは [0, 3] にクランプ（符号制約）、Core ML 等の外部依存なし、
  学習は決定的で `swift test` で検証できる
- **既知の限界**: 1 タップ記録は「調子が悪い時ほど記録する」選択バイアスを持ちうる。
  補正はせず、限界として明記する（§7 の HealthKit 連携が将来の緩和策）
- **体質の事前申告**（2026-09-09 追加、2026-09-10 改訂）: オンボーディングで「どんな時に不調になりやすいか」
  （低気圧・雨・湿気・寒暖差、複数選択・任意）を 1 回聞き、事前重みを傾ける。
  **気象要因は独立ではない**（雨の日は高湿で、低気圧・気圧変化を伴う）ことを大前提とし、
  申告 1 件は主要因を 1 → 1.75、気象的に相関する要因を 1 → 1.35 に傾ける。
  本人が名指しした要因が実際の機序とは限らず、切り分けは記録が溜まってから回帰が行う。
  相関する要因にも傾ける根拠は集団データにある: 降雨の独立寄与は気象特徴のうち最下位か有意差なしで、
  湿度・気圧が実質を担っている（`docs/riskengine-api.md` 参考文献 [1][4]）。
  **文献上も、自分の引き金を正確に知っている人は多くない**（信じている人 62% に対し実測で
  敏感 51%、しかも要因の取り違えが普通 — Prince 2004 ほか、
  `docs/research/2026-09-10-weather-attribution.md`）。申告 UI は「わからない」を既定の道とし、
  記録時に主観的な原因を聞かない。**学習結果が申告とずれても、本人に「申告が間違っていた」
  とは伝えない**（ユーザー決定。相関レポートは申告に言及せず記録の記述だけを出す）。
  低気圧ではなく高気圧・上昇に反応する個人も実在するため
  （Becker 2011）、個人化データが溜まった段階で絶対気圧の高側規則を検討する（§3.2 のクランプが
  その布石）。
  申告は本人の中で定数であり切片と共線するため**説明変数にはなれない**。事前分布に入れることで
  記録ゼロの初日から閾値に効き、記録が溜まれば縮小推定が申告を自然に上書きする。
  **申告は初期値、記録が真実**という序列。申告の固定ルール化（「雨なら必ず通知」）はしない
- 実装は `PersonalRisk` ターゲット。API 正典は `docs/personalrisk-api.md`

### 6.6 任意の状態入力と HealthKit の役割分担（2026-09-09 決定、実装は v1.1）

「今日の寝不足・ストレス」は日々変わるため、体質申告と違い**説明変数になれる**。
§6.3 が名指しする交絡因子を変数化し、気象の重みから交絡の寄与を分離する。
「あなたの頭痛は気圧より寝不足と相関しています」という記述レポートも可能になる。

- 入力 UI は**保存後の休む画面に任意チップ**として置く。§6.1「2 秒で完了」の
  コア動線には 1 タップも足さない。未入力がデフォルトで、スキップに罰がない
- **睡眠**: Watch があれば HealthKit の客観値（睡眠時間・段階）を優先し、
  手入力チップは非 Watch ユーザーのフォールバック
- **ストレス**: HealthKit に直接値がなく HRV が代理指標に留まるため、
  手入力チップは Watch の有無によらず価値が残る
- 任意入力は「ほとんど欠損」が前提。欠損の統計設計（欠損指示変数など）は
  v1.1 の多変量相関エンジンの設計に含める
- `HealthCheckIn` は optional フィールドの追加で過去記録と互換のまま拡張できるため、
  v1.0 でのスキーマ前倒しは行わない

### 6.7 記録で解放される着せ替え（2026-09-09 決定、素材先行）

体調記録の累計日数で、きあぼうの色・模様・小物を本人が選べるようになる。
学習結果で自動変化する案から、**本人が選ぶ着せ替え**へ変更（ユーザー提案）。

- 解放は**連続ではなく累計**の記録日数。休んでも取り上げない。記録成功時だけ進捗が進む
- 快適さの設定（無地背景・明るさ・ゆらぎ停止）には解放条件を付けない
- 背景も解放対象（2026-09-11、ユーザー制作の 11 種を採用）。入り江と無地は最初から、
  11 種は累計 5 日・10 日で解放（設計値）。詳細は `docs/kiabou-integration.md` §3.3
- **着せ替えの解放と通知学習の成熟は同一ではない**として表示も分ける
  （3 日で色が選べても「あなたの傾向が分かりました」とは言わない）
- 素材は制作・検証済み（3 外観 × 色だけ/模様あり + 交換用小物、GLB/USDZ 50 ファイル）。
  詳細は `assets/kiabou/variations/README.md` と `ASSETS.md`。色/模様は 2026-09-10、衣装ペルソナ 5 種は 2026-09-11 に実装済み

### 6.8 スコアの根拠画面（2026-09-11 決定）

配点の根拠にした文献を本人が確認できる画面を、設定タブに置く。§6.3 の誠実さの表面であり、
集団統計を売りにする競合との差でもある。App Store の説明文には載せず、審査メモから指す。

- **場所**: 設定 → 「このアプリについて」グループ → 「スコアの根拠」。グループは 4 項目以内の規律を守る
- **構成**: 冒頭に一文「これらの研究はこのアプリを検証したものではなく、配点を決める参考にしたもの」。
  続けて規則ごとに「何を根拠にしたか」を一行で述べ、文献を著者名・誌名・DOI で列挙する。
  DOI は `https://doi.org/` へのリンクにする
- **文言の線**: アプリ名（他社製品）は出さない。「実証」「予測」「診断」を使わない。
  設計の根拠と効果の実証を混ぜない（Guideline 1.4.1 と §9 の医療表現の線）
- **正典**: 文献一覧は `docs/riskengine-api.md` の参考文献節。アプリ内の一覧はそれを写したもので、
  増減があれば仕様書を先に更新する
- **App Store**: 説明文には「配点は査読済みの研究（4 万人規模の記録データなど）を参考に設計しています」
  の一文だけ。書誌は Review Notes に列挙する
- **Review Notes の定型文**（提出時にそのまま使う）:
  「本アプリは医療的な診断・予測を行いません。気象データの提示と自己記録の可視化を行うもので、
  リスク配点の根拠にした査読済み文献は 設定 → スコアの根拠 に掲示しています
  （Katsuki 2023 Headache doi:10.1111/head.14482、Becker 2011 Cephalalgia doi:10.1177/0333102410385583、
  Portt 2026 Environ Epidemiol doi:10.1097/ee9.0000000000000475、Dixon 2019 npj Digit Med doi:10.1038/s41746-019-0180-3）。
  文献はアプリの効果を検証したものではなく、設計の参考にしたものである旨をアプリ内でも明示しています。」

## 7. Apple Watch / HealthKit

### 7.1 なぜ効くのか

§6.3 で挙げた交絡因子の問題を、推測ではなく**実測**で解決できる。

特に **HRV（心拍変動）** が重要。気象病の機序は「気圧変化 → 交感神経の過剰興奮 → 自律神経の乱れ」であり、
HRV はまさにその自律神経のバランス指標。機序の中心に計測値が対応している。

| HealthKit データ | 役割 |
|---|---|
| HRV (SDNN) | 自律神経の状態。気圧変化への反応 |
| 安静時心拍数 | ベースラインからの逸脱 |
| 睡眠時間・睡眠段階 | 片頭痛の主要トリガー。交絡因子の実測 |
| 手首皮膚温 | Series 8 以降。体調変動の指標 |
| 月経周期 | 女性ユーザーでは気圧より支配的なことがある |

相関エンジンの入力が「気圧のみ」から「気圧 × 睡眠 × HRV × 周期」になることで、
「気圧が下がる日でも、睡眠が取れていれば出ない」といった個人ルールまで導出できる。

記録を HealthKit の頭痛カテゴリへ書き戻し、ヘルスケアアプリ側からも見えるようにする。

### 7.2 収益との関係

watchOS に広告 SDK は存在しない。
さらに文字盤コンプリケーションでリスクが見えると、ユーザーは iPhone アプリを開かなくなる。
1 セッションあたりの広告面数だけを見れば明確なマイナス。

しかし広告収益は `DAU × 面数` で決まる。
**文字盤に常駐して毎日目に入り、アンインストールされない**効果のほうが大きい。
継続率が 2 倍になれば面数が半分でも上回る。コンプリケーションは収益的にもプラスと判断する。

その上で線引きする。

- コンプリケーションはリスクレベルのみ表示（Tier 0 相当の情報）
- Watch 通知の詳細を見るタップ先は iPhone アプリ
- 相関レポート・詳細予報・複数地点は iPhone のみ = 広告面を温存
- **Watch 連携そのものをリワード広告の後ろに置かない。** 体調系の中核機能を広告と交換させない

### 7.3 遵守すべき制約

**HealthKit のデータを広告に利用することは App Store の規約で明確に禁止されている。**
広告一本で収益を立てる以上、ここは事故ればリジェクト事由になる。

§3 のモジュール分離により、広告 SDK が動くモジュールから健康データ型へ型レベルで到達できないようにする。
サーバーを持たないため、そもそも外部へ送出する経路が存在しない。

## 8. 広告設計 — 4 層モデル

### 8.1 前提の確認

気象病アプリは 1 セッション 10〜30 秒。「今日どう？」を見て閉じる。
**画面遷移の回数で広告を稼ぐのは物理的に成立しない。**
ここを見誤ると遷移を水増しする設計になり、競合と同じ体験になる。

方針は「面を増やす」ではなく、**自発的に潜りたくなる深さを作り、そこへ広告を集中させる**。

### 8.2 層構成

**Tier 0 — 広告を置かない聖域**

起動直後のメイン画面（今日のリスク）、通知タップで開いた画面、1 タップ記録 UI。
広告ゼロ・通信ゼロ・キャッシュから即描画。

体調が悪いときに開く画面だから。競合との差はこの 1 画面で付き、低評価レビューへの防波堤にもなる。

**Tier 1 — インフィード・ネイティブ広告**

時間別リスト、週間予報リストの中に数件おきに 1 枠。
スクロールで可視域に入って初めてロードする。
バナーより単価が高く、レイアウトを自分で組めるので表示がガタつかない。

**Tier 2 — インタースティシャル**

画面遷移時。頻度制御がすべて。

- 起動後の最初の遷移では出さない
- 遷移 4 回ごと
- 前回表示から 3 分以上
- 1 日 6 回まで
- 通知経由の起動は遷移カウントに含めない

AdMob は予期しない全画面広告をポリシー違反としているため、この制御は収益とコンプライアンスの両面で必須。

**Tier 3 — リワード動画**

主力。ユーザーが自分で押すため不満が出にくく、単価も全フォーマット中で最も高い。

| 解放するもの | 期限 |
|---|---|
| 個人相関レポート | 7 日間 |
| 地点の追加（2 件目以降） | 30 日間 |
| 7 日先の詳細予報 | 24 時間 |
| 過去ログのグラフ表示 | 7 日間 |

期限付きにするのは再収益化のため。ただし短すぎると嫌がらせになるので上記が上限。

**App Open 広告**

コールドスタートでは出さない（起動体感を殺す最大要因）。
バックグラウンド復帰時のみ、かつ前回表示から 4 時間以上経過している場合に限る。通知経由の起動は除外。

### 8.3 軽さを守る実装上の要件

- Google Mobile Ads SDK の初期化は**メイン画面の描画完了後に非同期実行**。起動のクリティカルパスに乗せない
- 広告表示は `AdProvider` プロトコル 1 枚に閉じ込め、後からメディエーションへ差し替えても画面側を触らずに済むようにする
- 初回リリースは AdMob 単体。DAU がゼロの新規アプリでは他ネットワークがフィルを返さないため、
  メディエーションは実装と同意管理の負担だけが先行する。トラフィックが立ってから追加する

## 11. データ源の調査結果（2026-08-30 実施）

当初案の Met.no / Open-Meteo は**いずれも本アプリでは使えない**ことが判明した。
両者ともサーバーの設置を要求するため、§3 のサーバーレス設計が成立しなくなる。
代替として Apple WeatherKit を採用する。

### 11.1 Open-Meteo — 使用不可

利用規約で、広告を表示するアプリは明確に商用利用と定義されている。

> "You may only use the free API services for non-commercial purposes."

商用にあたる例として "Operating websites or apps that have subscriptions or **display advertisements**" が挙げられている。
本アプリは広告のみで収益を立てるため、無料枠は使えない。

有料プランは `customer-api.open-meteo.com` への API キーが発行される方式。
キーをアプリのバイナリへ埋め込むと抽出されるため、プロキシサーバーが必須になる。

### 11.2 Met.no — 使用不可

API キーは不要で商用利用の明示的な禁止もないが、規約が**モバイルアプリからの直接アクセスを否定している**。

> "Browsers and mobile apps should not contact the API directly, but instead use a local proxy (backend for frontend) server."

さらにレート制限が「アプリ全体で 20 req/s（クライアント単位ではない）」と規定されており、
ユーザー数が増えた時点で規約違反が避けられない構造になっている。

> "Anything over 20 requests/second per application (total, not per client) requires special agreement."

キーが不要な点だけを見て採用すると、スケールした瞬間に破綻する。

### 11.3 Apple WeatherKit — 採用

iOS 専用アプリであることが、ここで決定的な利点になる。

| 項目 | 内容 |
|---|---|
| 呼び出し方 | Swift の第一者フレームワーク。端末から直接呼ぶのが正規の使い方 |
| API キー | 不要（entitlement ベース）。バイナリ埋め込み問題が存在しない |
| 気圧 | `pressure` = 海面気圧（ミリバール = hPa）。`pressureTrend` も提供 |
| その他 | 気温・湿度・降水確率・10 日先までの毎時予報。リスクエンジンの入力を全て満たす |
| カバー範囲 | 全球 |
| 商用利用 | 可 |
| 無料枠 | 500,000 コール/月が Apple Developer Program（$99/年）に含まれる |
| 帰属表示 | Apple Weather の商標表示とデータソース帰属リンクが必須 |

**プロキシサーバーが不要なので、§3 のサーバーレス設計がそのまま維持できる。**

採算の確認。1 ユーザーあたり 1 日 4 回取得として月 120 コール。

| 段階 | 月額 | 収容 DAU |
|---|---|---|
| 無料枠 500K | $0 | 約 4,100 |
| 1M | $49.99 | 約 8,300 |
| 5M | $249.99 | 約 41,000 |
| 10M | $499.99 | 約 83,000 |

41,000 DAU 規模の広告収益は月 $250 を大きく上回るため、経済的に問題なくスケールする。

### 11.4 気象庁 — v1.0 では見送り

利用規約自体は問題ない。政府標準利用規約（公共データ利用規約 第1.0版）に準拠しており、
**商用利用は可能**。ただし「出典：気象庁ホームページ（URL）」の表示と、加工した場合はその旨の明記が必要。

見送る理由は規約ではなく実装リスク。
既存コードが叩いている `www.jma.go.jp/bosai/...` は公式に API として提供されているものではなく、
気象庁サイト自身が使う内部エンドポイントである。予告なく変更・停止される可能性があり、
アプリから大量にアクセスする使い方は想定されていない。

WeatherKit の分単位降水予報（一部地域）が日本で利用可能であれば、そちらで代替する。

### 11.6 WeatherKit のスケールの罠（Plan 2 の必須要件）

コードレビューで判明した、静かに壊れる種類の不具合。

WeatherKit の `humidity` と `precipitationChance` は **0...1 の比率**で提供される。
一方 RiskEngine のスコアリング閾値は既存 TS 実装を引き継いで **0〜100** を前提としている
（湿度 75 以上、降水確率 60 以上など）。

アダプタ層で 100 倍を忘れると、湿度スコアと降水スコアが**恒久的に 0 のまま**になる。
例外も警告も出ず、ただアラートが発火しなくなるだけなので、最も発見が遅れる壊れ方をする。

範囲バリデーションでは検出できない点に注意。誤って `0.85` が渡された場合でも
`0...100` の範囲内に収まってしまうため、クランプも `precondition` も無力である。

**したがって Plan 2 のアダプタには、変換が行われていることを検証するテストを必ず含める。**
具体的には、WeatherKit 相当の入力（`humidity: 0.85`）を与えたとき
`WeatherPoint.humidity == 85` になることを確認するテスト。
